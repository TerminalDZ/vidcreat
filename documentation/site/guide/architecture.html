1. The idea in one minute ​

ReelForge takes two inputs:

  • A voice recording (voice.wav) of you reading your script.
  • One file, episode.yaml, that describes the script line by line, the scenes, the elements (titles, diagrams, code, tables, maps…) and on which spoken word each element appears.

It produces a vertical 1080×1920 video at 30 frames per second, ready for TikTok, Reels and Shorts, with word-by-word captions in Arabic and English, procedurally generated sound effects, audio mastered to −14 LUFS, and a publishing sheet.

Three principles govern everything:

PrincipleMeaning
Fully localNo cloud, no account, no internet access while rendering (the network is blocked inside the browser).
No AI in the render engineThe engine generates no voice and no images, and no model runs while rendering. The optional helpers (cue alignment, scene suggestions) are local, opt-in authoring aids (ADR-013); scene suggestions reach a cloud service only if you configure one.
DeterministicThe same inputs give exactly the same pixels, in any order and with any number of workers.

The technical trick: a web page (HTML/SVG/Canvas) draws the frame at any time t through a pure function render(t), headless Chromium screenshots every frame, and FFmpeg turns the images into a video.

Around this core sit two authoring layers: a dashboard and visual editor for people, and one tool registry (24 tools) that serves AI agents over MCP and REST, plus 12 industry packs whose templates have slots, so even a small model can produce a valid episode.

5.3 The golden rule: the Timeline is the only contract ​

core knows nothing about the DOM, and runtime knows nothing about YAML or zod. The only thing that passes between them is the Timeline object defined in types.ts. As a result:

  • The runtime bundle stays small (no zod, no YAML library).
  • core can be tested without a browser.
  • A test checks that the component list in core (the schemas) matches the one in runtime (the drawing code).

A second rule of the same kind applies to agents (ADR-014): no transport declares a tool of its own. Every tool lives in packages/studio/src/tools/, and MCP stdio, MCP HTTP, REST, the OpenAPI document and the server card all pick it up automatically.

In words:

  1. Write. One sentence per line (about 2.3 words per second; 45 seconds ≈ 100–110 words). The first line is the hook, the last one a call to action.
  2. Create. reelforge new ep10 or the New episode button creates the folder from the generic template, or from an industry pack template (reelforge new ep10 --pack healthcare --slot org="…").
  3. Estimate timing. Before recording, draft cues give realistic timing for previews.
  4. Design. Add scenes and elements (by hand, from a blueprint, or from suggestions) and make each element enter on the word that names it.
  5. Validate and preview. validate reports V-1…V-14 issues, and snap writes PNG frames at given times.
  6. Record and time. Record voice.wav; automatic alignment marks every line and word; listen once in Cues mode and fix any line by pressing Space.
  7. Render. render writes the outputs to out/.

Because elements are anchored to words, not seconds, re-recording one sentence only means aligning again or re-marking one cue, and everything after it stays in sync.

An AI agent takes the same path through the tools: create_from_template or create_episode, then add_scene or edit_episode, then validate_episode and preview_frames, then align_cues and render_episode (see §15).

8. Time: cues, words and time expressions ​

This is the cleverest part of the project and worth understanding well.

8.1 Three layers of time ​

mermaid
flowchart TB
    A["cues.json<br/>l1: 0.3, l2: 4.0, l3: 6.8 …<br/>(draft, auto-aligned, or marked with Space)"]

8.2 Cues ​

A cue is the start of a line. A line ends where the next one starts (or at the end of the audio for the last line). The shape of cues.json:

json
{
  "version": 1,
  "audio": { "file": "voice.wav", "duration": 45, "sha1": "…" },
  "cues": { "l1": 0.3, "l2": 4, "l3": 6.8 },
  "words": { "l2": [4.0, 4.31, 4.9] },
  "draft": true
}
  • Where do they come from? Three sources, all writing the same file:
    • Draft (draft: true): an estimate in compile.ts (draftCues): 13 letters per second plus a 0.35 s gap between lines, starting at 0.2 s. When a recording exists, the dashboard stretches the estimate linearly to its length.
    • Automatic (auto: true): alignment from the recording with Auto-mark from voice, reelforge align or the align_cues tool (see §24). It places lines and words; a V-3 info message stays until you save once in Cues mode.
    • By hand: in Cues mode you press Space at the start of each line while listening (at 0.5×–1×). Optionally, Snap to voice moves the mark to the nearest real onset within ±120 ms (see §12).
  • ADR-004 and ADR-013: ADR-004 chose hand-marked cues because the render engine must contain no machine learning. ADR-013 then allowed the computer to suggest cues, provided they remain an authoring aid: they never replace what a person marked without confirmation, and no model runs at render time.
  • Protection: if the voice file changes after cues were marked, its sha1 differs and V-4 warns.

8.3 Estimating word times ​

When cues.json has no word times, words.ts (estimateWordStarts) spreads the line's duration over its words in proportion to each word's letter count (minimum 2), after reserving 0.18 s as an end-of-line pause.

A real example from examples/promo/intro:

Line l1 = "What if your voice could direct the whole video?", cue = 0.3, next line at 4.0.

text
span     = 4.0 − 0.3 − 0.18 = 3.52 s
weights  = What 4, if 2, your 4, voice 5, could 5, direct 6, the 3, whole 5, video 5  → total 39
voice    = 0.3 + 3.52 × (4+2+4)/39 = 0.3 + 0.903 = 1.203 s

So l1:'voice' is 1.203 s by estimate. When cues.json holds word times (from automatic alignment, or from word mode with the W key) and their count equals the number of words exactly, they replace the estimate; otherwise V-3 warns and the estimate is used.

8.4 Time expression grammar ​

Defined in time.ts:

text
expr   := base offset*
base   := NUMBER "s" | NUMBER                ← absolute seconds
        | LINE_ID                            ← line start
        | LINE_ID ".end"                     ← line end
        | LINE_ID ":" 'word' ("#" N)?        ← a word (its Nth occurrence)
        | LINE_ID "." N                      ← word number N (0-based)
        | "@" SCENE_ID (".start" | ".end")?  ← scene start/end
offset := ("+" | "-") NUMBER "s"?
ExpressionMeaning
12.5s / 12.5second 12.5
l7start of line 7 = its cue
l7.endmax(start, next − 0.15): 0.15 s before the next line starts
l7:'bucket'the first occurrence of "bucket" in line 7
l7:'the'#2the second occurrence of "the"
l7.3the fourth word (0-based)
@hook.endthe end of scene hook
l7:'x'+0.40.4 s after the word (several offsets can be chained)

Word matching is forgiving: before comparing, punctuation, Arabic diacritics and tatweel are removed, أ إ آ are folded to ا, and letters are lowercased. A multi-word phrase can be matched too. When the word is not found, the result is a V-2 error with the closest word suggested (Levenshtein).

YAML rule: wrap the expression in double quotes when it contains : or ', e.g. at: "l3:'bucket'".

  • Failure does not stop everything: an element with an unknown component or invalid props is dropped and reported, but a Timeline is still returned (with fallbacks), which is why the editor can keep showing the "last good" version.

9.5 Captions and Arabic ​

This part is subtle, because mixing Arabic and English (الـ client) confuses most engines. The solution lives in captions.ts (logic) and runtime/captions.ts (drawing), documented in ADR-007:

  1. Direction per line: RTL when the line contains an Arabic letter.
  2. Grouping words into tokens:
    • Consecutive Latin words merge into one token: "Duplicate Charge".
    • A word ending in tatweel ـ is glued to the next one with an NBSP: الـ client never breaks across lines.
  3. Bidi isolation: inside each token, the Latin parts are wrapped in <bdi>. The whole token is inline-block and nowrap, so it behaves as one block in paragraph order. Punctuation such as ؟ stays outside the isolation and lands in the right place.
  4. Chunking: at most 34 characters per chunk (from the theme). A long chunk is split at the punctuation mark nearest the middle, or in the middle. break: ['word'] on a line forces breaks.
  5. Karaoke: every token carries its start time. While drawing, the current word uses the active color (lime), past words the normal color, upcoming words are faded (future_opacity 0.32), and English inside Arabic uses the english color (cyan). The active word pulses slightly.

The .srt output wraps Arabic lines in the Unicode RLE…PDF marks so players display them correctly.

Why static grain? (ADR-011): noise that changes every frame cannot be compressed. Measured: no grain 1.9 Mb/s, animated grain 64.5 Mb/s, static grain 5.9 Mb/s. Platforms remove it when re-encoding anyway.

10.6 How a component is written ​

ts
interface RuntimeComponent {
  name: string;
  handles?: EnterAnim[]; // animations the component draws itself (title/code: type, arrow: draw, trap: glitch)
  mount(root, props, theme, ctx): Instance; // once: build the DOM
}
interface Instance {
  update(t, local, state): void; // every frame: a pure function of t
}
  • mount builds the DOM once and may measure text (fitText shrinks the font by binary search until it fits).
  • update runs every frame and must be a function of t only.
  • Most components are HTML/CSS. SVG is used for arrows, the bucket, checklist marks, icons, charts, maps and the QR code. Canvas is used for particles, the glow, the grid and grain.
  • DOM writes go through a cache (css(), attr(), text()) that only writes when a value changed, which makes drawing much faster.
  • measure() skips components without measurable text (arrow, particles, trap, icon) and measures the rest in their settled state near the element's end.

10.7 Determinism in the browser ​

  • No Date.now, Math.random, setTimeout or requestAnimationFrame in runtime code.
  • The base CSS forces animation: none !important; transition: none !important on everything.
  • Randomness comes from rnd(seed) and mulberry32(seed) in the audio package; the seed is hash(element id) XOR timeline.seed.
  • Particles are computed in closed form from t − start, not simulated step by step, so frame 500 can be drawn before frame 10.
  • All images are decoded (img.decode()) before the first frame, so no frame depends on load timing.
  • One test renders the whole gallery forwards and backwards and compares the DOM; another compares SHA-1 hashes of the JPEG frames.

11.4 Encoding ​

Shared H.264 settings: libx264, profile High, GOP 60 (two seconds), 2 B-frames, constant frame rate, and the YUV420_TV color conversion:

text
-vf scale=out_range=tv:out_color_matrix=bt709:flags=accurate_rnd+full_chroma_int,format=yuv420p
-pix_fmt yuv420p -color_range tv -colorspace bt709 -color_primaries bt709 -color_trc bt709

The story behind this line: JPEG frames are captured in full range. Since FFmpeg 7, -pix_fmt yuv420p alone no longer converts the range, so the video came out full range, ffprobe saw yuvj420p, and the compliance check failed (some platforms reject it too). The fix: a scale filter that really converts to limited-range BT.709 (the HD and phone video standard), with tags that say so. It is applied to the intermediate segments and to the final encodes.

OutputVideoAudioNotes
MasterCRF 18, preset slow (medium with --fast)AAC 192k, 48 kHzarchive quality
Sharetwo passes at a computed bitrate, maxrate 1.5×, bufsize 3×AAC 128knever over the size cap, never above the master's bitrate
Partlike master, but always mediumAAC 192kpartial renders

The share formula (ADR-006):

text
video_kbps = floor(MB × 8192 × 0.97 / duration) − 128      (0.97 = 3% margin for the MP4 container)
           then clamped to 250…8000 kb/s, and never above the master's bitrate

A real example: a 45 s episode with a 28 MB cap → floor(28×8192×0.97/45) − 128 = 4944 − 128 = 4816 kb/s. That is exactly what the render printed: share video 4816 kb/s. If the file still comes out over the cap, it is re-encoded once at 90% of the rate.

The compliance check checkCompliance (ffprobe): h264, High, yuv420p, 30/1, AAC, 48 kHz, the moov atom before mdat (faststart: playback starts before the download finishes), and the size within the cap.

The contact sheet sheet.jpg: 12 evenly spaced frames in a 4×3 grid, 360×640 each.

13.3 Structured edits that keep comments ​

The editor never rewrites the file from scratch. It sends small operations addressed by YAML path:

json
{
  "label": "Move hook_title",
  "ops": [
    {
      "op": "set",
      "path": ["scenes", 0, "elements", 1, "place"],
      "value": { "x": 60, "y": 180, "w": 960, "h": 240 }
    }
  ]
}

Operations: set, delete, insert, move. edit.ts applies them to the YAML document tree (the yaml library), not to a JSON object, and the edit_episode tool uses the same code:

  • Changing a scalar edits the node in place, so quoting style and a # keep me comment survive.
  • Small objects are written in flow style ({ x: 1 }), following the file's existing indentation.
  • Deleting cleans up empty containers (an enter: {} disappears).
  • Writes are atomic (temporary file, then rename).

History: up to 200 steps in server memory, covering episode.yaml, cues.json and the assets. When the file is changed outside the editor, the history is cleared (so undo never overwrites your edits).

19. Determinism ​

Why does "same inputs = same frames" matter? Because it lets frames be rendered in any order on any number of workers, lets you re-render just a part, keeps scrubbing back and forth in the editor correct, and makes visual tests trustworthy.

How it is guaranteed (ADR-003):

Possible source of differenceHow it was removed
Wall-clock timerender(t) takes t as input; there is no clock in the runtime
CSS animationsDisabled with !important in the base CSS
Randomnessrnd(seed) and mulberry32(seed); seeds come from the episode and element ids
Accumulated statestates are computed from scratch for each t; particles are closed-form
Fonts and imagesBundled locally and loaded before the first frame, checked by V-13; images decoded before the first frame
Browser rasterizationNo GPU, no LCD text/hinting, sRGB, scale 1, UTC, locale en-US
AudioEffects are generated from a seed, and the mix uses fixed settings
ModelsNever used while rendering; the renderer reads cues.json like any other file

The one exception: the final x264 encode may differ byte for byte between FFmpeg versions, but the captured frames themselves are identical.

22. Notes and things worth knowing ​

Studying the code turned up things that are not necessarily bugs, but knowing them saves time:

Behaviors that may surprise you:

  • The schema's default language is ar-EG, and the direction becomes RTL when any line contains an Arabic letter or meta.lang starts with ar.
  • audio.sfx: manual also ignores an explicit fx.sound, not only the automatic sounds.
  • Draft cues count letters at 13 per second, while automatic alignment weighs lines by syllables.
  • V-14 pacing is not checked with draft cues, because their speed is assumed, not measured.
  • --keep-tmp keeps temporary files on failure only, as its help text says.
  • Arrows and targets only connect elements of the same scene.
  • Progress notifications are only sent over stdio; MCP over HTTP answers with plain JSON.
  • MCP over HTTP and REST need the dashboard (reelforge studio) running; stdio does not.

Possible weak spots in the code:

  • Cancelling a render kills every ffmpeg process in the same process (killAll on a global list), which would matter if two renders ran in one process (the RenderRunner currently prevents that).
  • The 90% share re-encode sends no progress and does not respect the master bitrate cap.
  • On cancel, .srt and publish.md are not removed.
  • A network access attempt is only detected at the end of a worker's range, and the range is then retried although it will most likely fail the same way.
  • screens.ts has a line multiplied by * 0, so phone notifications coming from states all appear at the same moment.
  • HEAD = 132 (the timeline's track label width) is duplicated in JS and CSS.
  • timeexpr.ts in the client imports from core through a relative path instead of the package name.
  • pnpm typecheck uses tsc -b, which also writes build output.
  • CI does not run validate on the Arabic examples (season1-arabic) or the pack examples.
  • The renderer's unit tests cover only its helpers (the formula, range splitting, MP4 atoms); the render pipeline, workers and encoding are covered by the browser tests.

24.1 Automatic cues (DSP, no model) ​

mermaid
flowchart LR
    W["voice samples"] --> E["10 ms energy track<br/>(block sums, O(n))"]
    E --> T["adaptive threshold<br/>percentiles + hysteresis"]
    G["Silero VAD mask<br/>(optional gate)"] -.-> T
    T --> M["voiced mask<br/>drop clicks < 30 ms<br/>fill gaps < 50 ms"]
    M --> P["pauses = candidate<br/>line boundaries"]
    S["script lines →<br/>syllable weights"] --> DP
    P --> DP["DP: N lines over M pauses<br/>cost = (ln(voiced/expected))²<br/>− reward(pause length)"]
    DP --> R["refine to the sample:<br/>first 1 ms above threshold"]
    R --> L["line cues + confidence"]
    L --> WD["words: pauses inside the line ↔<br/>punctuation (DP), syllables,<br/>energy valleys"]
  • The expected weight of a line is the sum of the syllables of its words (vowels for Latin script, consonants and long letters for Arabic).
  • The DP picks one boundary per line among the silences so that each line's voiced time (not its total time; pauses do not count) is proportional to its weight, preferring long pauses. The search is bounded by a 1:5 ratio window, so 10 minutes and 120 lines take ~0.2 s.
  • Words: pauses inside a line are matched to word gaps (a word ending in punctuation is more likely), the rest is spread by syllables and moved to a nearby energy valley when there is one close enough.
  • A smart threshold tied both to the noise floor and to the speech level; otherwise digital silence (−120 dB) makes it catch the breath before a word.
  • Confidence: each line gets a 0..1 value, and the editor shows weak lines in amber so you listen to them first.

24.2 Whisper + matching against the known script ​

mermaid
sequenceDiagram
    participant A as alignEpisode

  • Whisper's text is not trusted: "ReelForge" may be heard as "real forge", and spoken dialects are written many ways. Matching uses Levenshtein after letter folding (ة/ه, ى/ي, أ/إ/آ), with 1:2 and 2:1 merges and skips for extra (um) or missing words. In tests, 96–100% of words were matched.
  • Lag correction: Whisper timings lag by a roughly constant amount (~0.1–0.2 s). The lag is measured per recording (the median between Whisper's line starts and the real pause ends) and subtracted.
  • Fusion: when the DSP estimate of a word agrees with Whisper within 120 ms, DSP wins (sharper edges); otherwise Whisper wins (it does not drift).
  • Engine choice: --engine auto (default) uses Whisper when installed, else DSP. Sizes are tiny, base (default) and small. The model is loaded once and released after 3 idle minutes (~0.5–0.8 GB while loaded).

24.4 Suggestions (smart insert) and the LLM provider layer ​

  • Dictionary (instant, no model, suggest.ts): Arabic and English keywords → a component, with props taken from the line (numbers in words, "thirty thousand" → 30000; "X vs Y" → table columns; system parts like Client/DB → node), entering on the word itself (l3:'bucket'). Every suggestion is validated against the component schema. In tests, more than 150 suggestions for all example lines (Arabic and English) compile without a single error. This is what suggest_scene and suggest_scenes use by default.
  • Language model (optional, llm.ts): a JSON Schema built from the zod schemas (a oneOf over the candidate components with their exact props, and an enum of the line's actual words for the entry word), so the model cannot invent a component or a prop. Times are always derived from the word, elements are validated again, wrong answers go back to the model once or twice with the problems, and arrows pointing at missing elements become points. The offered list is kept small on purpose (title, chip, icon + the dictionary's picks), because small models on laptops are slow.
  • The provider layer (providers.ts): one function, chatJson, returns a JSON object for a schema from any of three:

Privacy note: if you configure a cloud service (REELFORGE_LLM_API_KEY), the line and its context are sent to it; a local server keeps everything on your machine.

24.5 Safety and policies ​

  • Cues a person marked are never replaced without confirmation (force, --force, or a dialog in the editor). An automatic cues.json carries auto: true (a V-3 info), cleared by the first manual save in Cues mode.
  • In the editor the replacement goes through the undo history, so Ctrl+Z brings the old cues back.
  • Only one alignment runs at a time per server (409 while one is running).
  • Models are never used while rendering, and only files verified by setup are ever loaded.
  • Scene suggestions contact no external service without your explicit configuration; the default is a local server on 127.0.0.1.
